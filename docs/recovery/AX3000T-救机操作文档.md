# 小米 AX3000T（RD03）iStoreOS 救机操作文档

更新日期：2026-09-19  
依据：本机两次实际恢复记录，尤其是 2026-09-19 保留原配置恢复成功的过程。

## 1. 适用范围与当前结果

本说明适用于**本次实测的 AX3000T RD03、原厂 U-Boot、下表所示分区布局**。它不是所有 AX3000T 硬件版本或固件的通用刷机教程，不适用于直接套用到 `ubootmod` 布局。

本次恢复结果：

- 已从闪存正常启动 iStoreOS 24.10.8，内核 6.6.144。
- 原有可写数据分区保留，双频 `502` 和 `502-IoT` 恢复。
- SSH、管理页、dnsmasq 正常响应，OpenClash 核心进程存在。
- 恢复的是此前可用版本，**不是成功升级到 9 月 19 日的新镜像**。
- 验证时 WAN 没有获取上游地址，因此没有完成外网上网、代理节点和 UU 加速效果测试。

管理地址：`http://192.168.100.1`。

## 2. 最重要的经验

1. **先看串口实际报错，再决定修哪一层。** 橙灯闪、网口断续不能单独证明是 Wi-Fi、插件、内核或闪存硬件故障。
2. **先从内存启动已验证的恢复内核。** 本机原厂 U-Boot 可通过 TFTP 加载 FIT initramfs，再用 Linux 工具检查分区。
3. **U-Boot 与 Linux 的分区名称不同。** 同样叫 `ubi`，在两个环境里可能指向不同物理区域。
4. **保留并备份 `rootfs_data`。** 缺失 `rootfs` 不等于配置也丢了；本次完整配置和插件数据仍在。
5. **写入后必须按原始文件长度读回并比对哈希。** 返回成功、卷名存在、能列目录，都不足以证明镜像正确写入。
6. **不要把 U-Boot 的 `size 0x0` 当成卷为空的证据。** 同样的输出在本机成功启动时也出现过，必须结合实际数据和 FIT 校验判断。
7. 本次已经证明恢复可行，但**普通 sysupgrade 路径为什么失败尚未完整定位**。不要把一次救活等同于升级缺陷已修复。

## 3. 已确认的设备与分区

### 3.1 设备

| 项目 | 本机实测值 |
|---|---|
| 型号 | Xiaomi AX3000T / RD03 |
| 平台 | MT7981，ARM64，256 MiB RAM |
| NAND | 128 MiB；本次恢复内核识别为 ESMT |
| 交换芯片 | AN8855 |
| 引导方式 | 原厂 U-Boot，`bootcmd=bootxq` |
| 串口 | 115200、8 数据位、无校验、1 停止位、无流控 |
| 串口编号 | 9 月 15 日为 COM4；9 月 19 日为 COM5，重插后须重新确认 |
| U-Boot 地址 | `192.168.10.1/24` |
| 电脑 TFTP 地址 | `192.168.10.100/24` |
| Linux LAN 地址 | `192.168.100.1/24` |

### 3.2 本机 Linux 分区表

```text
mtd0  0x00100000  BL2
mtd1  0x00040000  Nvram
mtd2  0x00040000  Bdata
mtd3  0x00200000  Factory
mtd4  0x00200000  FIP
mtd5  0x00040000  crash
mtd6  0x00040000  crash_log
mtd7  0x00040000  KF
mtd8  0x02200000  ubi_kernel   起始 0x00600000，34 MiB
mtd9  0x04e00000  ubi          起始 0x02800000，78 MiB
```

**以上仅在现场 `/proc/mtd` 和启动日志一致时可用。** 不应按其他设备的 MTD 编号操作。本次修复未改写 BL2、FIP、Factory 等引导和校准分区。

### 3.3 名称对应关系

| 所在环境 | 名称 | 含义 |
|---|---|---|
| U-Boot | `ubi`，34 MiB | 从这里读取 `kernel` 卷 |
| Linux | `ubi_kernel`，mtd8，34 MiB | 对应上面的内核区域 |
| Linux | `ubi`，mtd9，78 MiB | 存放 `rootfs` 与 `rootfs_data` |
| Linux | `/dev/ubi0`、`/dev/ubi1` | attach 顺序生成的设备号，不能视为固定分区号 |

每次操作前用下列命令核实映射：

```sh
cat /proc/mtd
ubinfo -a
for d in /sys/class/ubi/ubi[0-9]*; do
    [ -f "$d/mtd_num" ] && echo "$d -> mtd$(cat "$d/mtd_num")"
done
```

## 5. 第一阶段：取得可控的串口

### 5.1 接线与电脑检查

- 使用适合路由器 TTL 电平的串口转接器，接 GND、交叉连接 TX/RX，路由器用原电源供电；不要用转接器电源脚给路由器供电。
- 网线连接电脑与路由器，TTL 保持连接。
- 确认当前 COM 号，不能沿用旧编号。
- 同一串口只保留一个操作者；`Access denied` 可能是端口占用，也可能是权限问题，不能直接判断硬件坏了。

Windows 只读检查：

```powershell
[System.IO.Ports.SerialPort]::GetPortNames()
ipconfig
netstat -ano -p udp | Select-String ':69\s'
```

如果需要检查占用进程，只定位相关串口/TFTP 程序，不能批量终止所有 PowerShell 或 Python。串口打开后先读取日志，不盲发升级选项。

### 5.2 截停启动循环

本机菜单出现：

```text
*** U-Boot Boot Menu ***
Hit any key to stop autoboot:
```

本次成功方式：看到这一提示后发送 `Ctrl+C`；菜单退出后还有一层自动启动倒计时，再发送一次 `Ctrl+C`，最终确认收到：

```text
RD03>
```

只有识别到对应提示才发送。不要把字符定时循环发送，也不要在已经开始擦写时打断操作。

如果没有重启循环且串口静默，先确认是否已停在输入提示。必要时用一次 `Ctrl+C` 返回控制台；不要先断电重启。

## 6. 第二阶段：通过 TFTP 启动内存恢复系统

### 6.1 设置电脑

先记录电脑有线接口现有地址和是否使用 DHCP。本机使用 `192.168.10.100/24`，不需要为恢复链路增加默认网关。接口编号和名称每次可能不同，须从现场结果确定。

修改 IP 需要 Windows 管理员权限；工具的“允许执行”不一定等于 Windows UAC 已提权。PowerShell 5 读取含中文的无 BOM UTF-8 脚本曾失败，建议使用正确编码或纯 ASCII 脚本。

Tftpd64 配置：

- Current Directory：`work\tftp` 的绝对路径。
- Server interface：`192.168.10.100`。
- 只启用 TFTP 服务；不需要另开 DHCP 服务。
- 目录中放入已校验的 `recovery.bin`。
- 确认没有第二个程序占用 UDP 69；如被防火墙拦截，只放行所需恢复程序/链路。

本机已有成熟的 Tftpd64 可用。不要重新使用此前出错的简化 TFTP 实现。

### 6.2 U-Boot 操作

以下命令在 `RD03>` 下执行，**不是 Linux shell 命令**：

```text
printenv bootargs bootcmd ipaddr serverip loadaddr mtdparts
setenv ipaddr 192.168.10.1
setenv serverip 192.168.10.100
tftpboot 0x46000000 recovery.bin
```

这些地址修改只用于本次内存会话，无需 `saveenv`。

必须看到完整传输：

```text
done
Bytes transferred = 10997348 (a7ce64 hex)
RD03>
```

再检查 FIT：

```text
iminfo 0x46000000
```

期望识别 AX3000T 的 kernel、initrd、设备树，并显示校验通过。若为 `Unknown image format` 或传输长度不一致，停在这里，不执行启动或刷写。

确认通过后：

```text
bootm 0x46000000
```

等待 `iStoreOS is ready!` 和激活控制台提示，按 Enter 进入 shell。此步骤从 RAM 启动内核，不把恢复镜像烧进系统分区。

## 7. 第三阶段：检查并保存现场

在 Linux 恢复系统内执行：

```sh
cat /proc/mtd
mount
ubinfo -a
```

确认当前 `/` 为 tmpfs 的内存系统，而不是正在使用闪存根文件系统。若内核分区尚未 attach，且 `/proc/mtd` 已确认 mtd8 为 `ubi_kernel`：

```sh
ubiattach -m 8
ubinfo -a
```

不要重复 attach 已挂接的分区，也不要看到报错就直接 `ubiformat`。

### 7.1 本次现场状态

```text
Linux ubi0 -> mtd9 / ubi
  卷 1 rootfs_data 存在
  卷 0 rootfs 缺失

Linux ubi1 -> mtd8 / ubi_kernel
  卷 0 kernel 存在且有效
  卷 1 rootfs 存在，内容有效，但位于错误区域
```

这与 9 月 15 日曾发现“kernel 内容为空”的情况不同，不能沿用旧诊断。

### 7.2 只读备份原数据

**仅在映射与本次一致时**，执行：

```sh
mkdir -p /mnt/saved
mount -t ubifs -o ro /dev/ubi0_1 /mnt/saved
du -sh /mnt/saved
ls -la /mnt/saved
tar czf /tmp/saved-overlay.tgz -C /mnt/saved .
sha256sum /tmp/saved-overlay.tgz
```

通过已建立的 SSH/SCP 通道把它复制到电脑，再在电脑执行 `Get-FileHash -Algorithm SHA256`，确认与路由器端一致。**电脑上的备份未校验前，不进行删除、格式化或替换数据分区。**

本次归档包含 `upper/`、`work/`、`.fs_state`、升级日志等。它是完整 overlay 救援归档，**不能当普通 sysupgrade 配置包直接上传恢复**。恢复时应在离线/内存环境内按目录结构和版本适配处理。

## 8. 第四阶段：本次成功的最小修复

下面是本次实际执行的特定修复，不是通用的一键脚本。必须同时满足：

- 分区与 UBI 设备映射已核实。
- mtd9 缺少 `rootfs`，仍保留 `rootfs_data`。
- mtd8 的 `kernel` 和额外 `rootfs` 内容与本节哈希完全一致。
- 已验证备份安全落到电脑。
- mtd9 有足够空闲 LEB，本次可用 139 个，每个 126,976 字节。

### 8.1 核实源数据

```sh
head -c 4349116 /dev/ubi1_0 | sha256sum
head -c 17582080 /dev/ubi1_1 | sha256sum
```

分别应得到第 4 节的 kernel 和 rootfs 哈希。任何一个不符，都不能继续按本节操作；应改为检查已验证、成套的固件文件。

### 8.2 先复制到内存并再次校验

```sh
head -c 17582080 /dev/ubi1_1 > /tmp/rootfs-repair.bin
sha256sum /tmp/rootfs-repair.bin
```

期望：`85de95ad…528407`，完整值见第 4 节。

### 8.3 在正确分区创建缺失卷并写入

**以下步骤写闪存。卷 ID 0 必须确认为空闲，不能用删除现有卷来强行满足命令。**

```sh
ubimkvol /dev/ubi0 -n 0 -N rootfs -s 17582080
ubiupdatevol /dev/ubi0_0 /tmp/rootfs-repair.bin
sync
head -c 17582080 /dev/ubi0_0 | sha256sum
```

逐条检查退出状态和输出；失败立即停止。读回哈希必须与源文件一致。卷分配后的容量会按 LEB 向上取整，哈希要按镜像原始长度计算，不能对整个填充后的卷直接求哈希。

这次未删除错误区域中额外的 rootfs 副本，也未重写 kernel 或 `rootfs_data`。成功启动前不做额外清理。

### 8.4 重启

```sh
umount /mnt/saved
sync
reboot
```

持续保存串口输出，确认读取 kernel、FIT 校验、挂载 squashfs 根文件系统、挂载 UBIFS overlay、进入用户空间依次成功。

## 9. 验收清单

启动一次后不要仅凭灯色宣布恢复完成：

```sh
cat /proc/uptime
mount | grep -E 'squashfs|overlay|ubifs'
df -h /overlay
free
iw dev
/etc/init.d/dnsmasq status
/etc/init.d/uhttpd status
pidof clash_meta
ubus call network.interface.wan status
logread | grep -E 'Out of memory|Killed process|AP-ENABLED|DFS-CAC|segfault' | tail -n 20
```

判定要求：

- uptime 持续增长，没有自动重启。
- 根文件系统和可写 overlay 均按预期挂载。
- 能访问 `http://192.168.100.1/cgi-bin/luci/`；未登录 LuCI 返回 403 时，应检查是否实际返回登录页，不能只凭状态码判断服务坏了。
- 2.4 GHz、5 GHz、IoT SSID 与原配置一致。
- 本次 5 GHz 自动选择信道 52，日志显示 60 秒 DFS CAC，随后 `AP-ENABLED`。这段等待不应误判为无线永久失效。
- 核心进程存在只能证明 OpenClash 已启动，不能替代代理节点、TCP/UDP/DNS 的实际连通测试。
- 本次启动有 Ruby 内存申请失败提示，但随后核心运行，约 114 秒时可用内存约 53 MiB，未观察到 OOM 杀进程。仍需结合后续负载观察。
- WAN 未获得地址时，明确记录“外网未验证”，不能把 LAN 管理页正常写成“互联网完全恢复”。

完成后停止临时 TFTP 服务并释放串口。电脑网络恢复到本次操作前的状态；本次 9 月 19 日发现电脑已有多组恢复地址，未擅自清除这些既有配置。

## 10. 不能再重复的误判与做法

| 误判/做法 | 本次经验 |
|---|---|
| `size 0x0` 就是空内核 | 错。成功启动同样出现，应检查实际字节和 FIT 哈希 |
| `ubi_kernel` 和 U-Boot 的 `ubi` 名字不同，所以启动槽一定错了 | 错。按物理范围和容量对照，本机两者对应同一区域 |
| 根文件系统放进 U-Boot 的 `ubi` 就足够 | 错。本机 Linux 从另一段 78 MiB 的 `ubi` 找 rootfs |
| 有效 FIT / 镜像哈希通过就证明安装布局正确 | 错。数据完整性与写入位置必须分别验证 |
| 橙灯闪就是插件冲突 | 无法证明。先分清 U-Boot、内核、根文件系统和服务阶段 |
| 持续按 Reset 总能清配置救回来 | 本机早期启动失败时未能解决；不能反复盲试 |
| 只看一次网卡 Disconnected 就说网线没接 | 启动循环会反复重置网口，应结合串口和持续链路观察 |
| 向带默认值的提示直接输入新 IP | 曾追加成无效地址。需先清空整行，或在控制台用 setenv |
| 自动给每个未知提示发送 Enter | 可能接受错误文件或选项。必须识别每一级实际提示 |
| 自写 TFTP 一直重试 | 曾发生 timeout 协商和第 256 块重复 ACK 处理错误；成熟 Tftpd64 成功 |
| 串口命令文件偶尔被锁就退出整个监听器 | 应处理瞬时 IO 错误，或使用已验证的单会话通信方式 |
| SSH 指纹变化时关闭所有校验 | 恢复系统与原系统的主机密钥可能不同，应经串口/已知记录确认，使用任务专用 known_hosts |
| 无差别恢复旧 `/etc` | 脚本和插件文件可能与新镜像不匹配；保留数据后再检查兼容性 |

## 11. 后续升级与交接要求

当前修复证明了“恢复已有可用系统”的方法有效，尚未证明 9 月 19 日新镜像和普通升级流程可靠。

再次升级前至少完成：

1. 备份当前完整配置、插件数据和关键分区；校验电脑端副本。
2. 检查升级脚本为何在 `Performing system upgrade...` 后留下缺失 rootfs 的状态，不预设原因是旧配置。
3. 核对 sysupgrade 包解出的 kernel/rootfs、目标 UBI 分区、内核模块 ABI 与 rootfs 中的工具是否配套。
4. 区分 `initramfs-kernel.bin`、factory UBI 和 sysupgrade tar 包，不互相改名冒充格式。
5. 固件写入必须在适当的内存升级环境进行，不能在仍挂载使用的闪存根文件系统上随意执行本次写卷命令。
6. 保持串口可用；写入后读回校验，重启后再确认配置持久化和网络。

交接时带上本文件、完整 overlay 备份、恢复内核、校验值以及当次串口日志。交接文档中的“必然可用”“一定是某原因”不能替代现场验证。
